# 第13章：业务图谱、设备身份与变更复核

属性图用节点、关系和属性表达业务联系，Cypher用于查找路径。业务投影把主库中已确认的关联转换成适合图查询的副本；Outbox记录待同步变更，查询后仍核对主库版本及权限。存在一条路径并不证明因果。

相关基础：[Neo4j与Cypher基本用法](基础知识/05_检索文档与多模态.md#t26)、[Outbox和可靠投递](基础知识/03_任务权限与文件存储.md#t11)、[数据范围](基础知识/03_任务权限与文件存储.md#t13)、[版本与哈希](基础知识/07_部署监控与工程验证.md#t41)。

## 13.1 三个实际问题

业务图谱帮助回答：一条异常能追到哪些交接、隐患、调查、工单和验收证据；规范变化影响哪些在途工单或有效经验；同一设备同一故障是否再次出现，历史措施和读数是什么。

PostgreSQL保存业务事实，Neo4j保存从这些事实构建的关系投影。图中的连接表示已记录引用或人工确认关联，不直接表达原因、措施有效率或自动审批结论。

## 13.2 先建立人工设备身份

站场属于组织，设备属于站场，设备编号在站场内唯一；故障类型使用组织内唯一编号。它们提供轻量身份登记，不承担完整设备ERP或GIS。

设备别名在站场内唯一。标识先做NFKC兼容转换，再折叠空白并忽略大小写，所以全角`ＶＡＬＶＥ  ２`与`valve 2`会冲突。不同站场可以有同号设备，不通过模糊名称自动合并。

正式编号同时作为保留别名。添加、撤回别名带`expected_version`和理由；正式编号别名不能撤回。停用设备保留历史，但不能新增或恢复关联。

`EquipmentAssociation`将事件、隐患或工单与设备及故障类型绑定，保存确认人、理由、版本和`source_revision`。来源指纹来自图谱记录的`binding_revision`；来源身份变化后，旧关联排除，须人工重新确认。工单正常推进状态不等于改变设备身份。

## 13.3 数据表与关系

业务身份与空间资料由站场、位置版本、设备、别名、故障类型和设备关联六类记录维护；图谱Outbox、投影状态和影响复核三类记录负责同步及后续处理。模型集中在[models.py](../app/modules/operational_graph/domain/models.py)，共九张表，按当前迁移顺序建库。

| 关系 | 业务含义 |
|---|---|
| SOURCE_OF | 交接、巡检等来源指向事件或隐患 |
| INVESTIGATED_BY / CITED_BY | 事件关联调查，知识被调查或问答引用 |
| FOLLOWED_BY / PROPOSED_ORDER | 事件或调查关联工单 |
| REMEDIATED_BY | 隐患关联工单 |
| RESOLVED_WITH / VERIFIED_BY | 工单关联整改，整改关联独立验收 |
| CONSOLIDATED_IN | 工单整理为经验 |
| SUPPORTS_EXPERIENCE / USED_IN | 经验被后续经验或调查使用 |
| AFFECTS / CLASSIFIES | 人工确认的设备、故障类型关联业务记录 |
| HAS_VERSION | 文档与其版本的结构关系 |

业务节点标签为`BusinessRecord`，关系为`BUSINESS_LINK`，与第8章RAG事实图分开。节点仅保存命名空间、快照、业务ID、类别和修订摘要；返回正文、措施和读数时从当前SQL记录读取。

## 13.4 站场位置与外部空间上下文

站场位置用追加版本记录来源、理由和确认人。位置沿人工确认的设备/事件关联使用，地图邻近关系不反向写成设备归属。位置更新、撤回或关联变更会使依赖它的外部证据失效；详见[第14章](第14章_气象预警与GIS地图工具.md)。

## 13.5 事务变更与完整快照发布

业务表的INSERT、UPDATE、DELETE触发器在同一数据库事务中写`business_graph_outbox`。业务回滚时通知也回滚。Beat每30秒投递同步任务，使用既有`knowledge_index`队列，排队或依赖故障可能延后执行。

同步取得事务级互斥锁，在可重复读事务中读取来源与可见通知。先写完整新Neo4j generation，再生成变更复核事项，最后提交SQL快照指针并消费本次实际读到的通知ID。

不能按“小于最大ID”删除通知：数据库序列发号顺序不等于事务提交顺序，较小ID可能晚提交。失败时保留通知和旧快照，下次重试；成功后旧快照保留一小时读取宽限，清理失败不撤销已经发布的结果。

实现见[projection.py](../app/modules/operational_graph/application/projection.py)、[change_capture.py](../app/modules/operational_graph/application/change_capture.py)及[Neo4j适配器](../app/infrastructure/knowledge/business_graph.py)。

## 13.6 查询时再次核对来源

`operational_graph:read`只允许调用图谱入口。每个节点仍检查原业务权限、数据范围、会议来源ACL等；路径上的所有中间节点都须可读。返回边与当前SQL引用逐条比较，撤回的设备关联即使仍在旧图中，也会立即被过滤。

保存为智能体证据后，还核对来源修订、边和权限。知识版本返回有效起止时间及`currently_effective`；跨越有效期边界也改变证据修订，避免沿用过期事实。

查询最多6层、1000条路径，每类来源和合计业务节点均受50000条容量限制。响应中的`source_changes_pending`提示待同步，`limited`提示路径限量，`complete`只描述当前权限和限定深度内的投影查询，不表示任意长度依赖已穷尽。

全局状态与强制同步仅向具有全局`operational_graph:manage`范围的人开放，普通读者不获得全局节点和通知数量。

## 13.7 规范变更怎样形成复核事项

知识撤回、到期或存在已生效可用新版时，沿正向依赖查找在途工单与审核有效经验。新版只提示适用性复核，不自动使旧版失效。影响遍历不走`HAS_VERSION`，防止旧版绕回文档再误伤仅使用新版的工单。

事项按来源、目标与变更签名去重；来源再变化时旧待办进入`superseded`。已关闭事项的目标再次改变且仍符合影响条件时重新复核并保留历史。决定带当前事项版本和`target_revision`，避免过期页面覆盖新状态。

| 决定 | 条件与结果 |
|---|---|
| not_applicable | pending时说明不适用理由后关闭 |
| reassessment_required | 记录措施安排，进入needs_action |
| revalidated | needs_action后提供新核验：当前工单最新实测整改的独立验收，或审核有效且关联替代原经验的新经验 |
| retired | 发现影响后目标已正式取消、撤回或被替代，记录退出理由；不冒充复测通过 |

整改和验收仍走原业务流程。复核通过`verification_id`引用实际记录；只有文字措施、旧验收或其他工单验收不能完成复测关闭。复核人还需目标业务审核范围及全部路径来源的读取权限。

## 13.8 重复异常怎样避免误算

仅按人工确认的同设备ID、同故障类型统计正式事件或已评估隐患。同一事件派生的隐患合并为一个批次；过期来源关联排除，并以`stale_associations`提示重新确认。

`orders`保存相关工单历史，`hazard_outcomes`保存直接隐患整改历史。工单措施还须确认对应当前设备故障；仅关联同一事件，不能自动视为该设备的有效整改。

`measured_accepted`要求关闭状态、最新实测整改、相应核验读数和独立通过的验收。历史记录只有closed而缺少材料，不能标成已实测。返回前后指标、措施、验收时间及之后再次登记的间隔；时间优先用事件发生时间，缺失时用登记时间并返回`time_basis`。

登记间隔不能自动证明措施无效或真实故障发生的精确间隔，样本范围也不能被包装成全企业有效率。

## 13.9 操作顺序与验证

先登记站场、设备、别名和故障类型，再读取业务记录的`binding_revision`并人工确认关联。同步后查询证据路径、知识影响或设备重复异常。查询未初始化返回409，正常初始化任务会建立首份投影。

权限包括`equipment:read/manage`与`operational_graph:read/manage/review`。设备管理员和图谱复核角色需与原业务角色组合使用，不替代事件、工单或知识权限。三个只读图谱工具已进入内部调查与MCP；MCP还可读取具体复核事项。

[图谱测试](../tests/test_operational_graph.py)验证标识纠错、晚提交通知、故障重试、权限、去重和复核闭环；[真实索引测试](../tests/test_knowledge_external.py)使用独立Neo4j命名空间验证实际查询。排障先查投影状态、Worker日志、来源容量和Neo4j健康，不直接将待办改成closed。
