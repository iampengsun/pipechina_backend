# 第5章：异常调查、MCP与维检工单

LangGraph用状态图组织调查步骤；ReAct让模型根据工具观察决定下一步；多角色将事实、风险、方案与复核分开。MCP让外部AI应用按统一协议调用能力，Agent Skills保存专业检查流程，上下文工程决定每个角色实际能看到哪些证据。

相关基础：[LangGraph与暂停恢复](基础知识/04_智能体与专业流程.md#t16)、[ReAct与动态调查](基础知识/04_智能体与专业流程.md#t17)、[MCP及Tasks](基础知识/04_智能体与专业流程.md#t18)、[专业技能](基础知识/04_智能体与专业流程.md#t19)、[角色证据上下文](基础知识/04_智能体与专业流程.md#t21)。

## 5.1 调查职责与执行路径

异常处置同时涉及事实、规范、历史经验、风险与行动建议。把这些问题一次交给模型，往往难以区分证据与判断。项目将职责分到多个节点，并保存输入、输出、工具证据和步骤。

| 节点 | 要回答的问题 | 主要输出 |
|---|---|---|
| Coordinator | 当前要调查哪些问题 | 技能选择、角色目标和动态子调查 |
| Evidence | 有哪些可见业务与规范证据 | 来源、版本、引用与未知项 |
| Experience | 历史经验是否适用于本次情况 | 采用/排除的经验及差异 |
| Risk | 证据支持什么分类与风险 | 风险候选和依据 |
| Plan | 可以建议哪些措施、由谁参与 | 方案、优先级和高风险动作 |
| Critic | 结论是否受证据支持、是否安全 | 待人工审核、修订或证据不足 |

协调者可按具体问题生成规范、历史、实测、复发和变更影响子调查；最多3个分支并行，各用独立数据库会话。取证结果汇总后，风险、方案与复核按依赖执行，Critic可触发受预算约束的修订。多角色可以使用同一个模型，差异在职责与证据规则。项目没有让多个模型自由协商后直接派发现场任务。

子调查由问题、初始查询、`completion_criteria`和`required`组成。分支先取证，再判断是否需要换查询条件或工具继续追查。例如历史泄漏调查先查事件，再查相应工单与实测；查询结果不足时保留未知项，不能把“未搜到”解释为事实不存在。工具按问题类型限制，读取大证据仍沿原证据回查接口。

默认每个分支最多4次工具查询、4次决策，执行时间90秒；整次调查仍受统一模型、工具、Token和费用预算约束。重复查询会停止该分支，已取得的证据保留；超时或上游服务错误作为未完成结果汇总。权限错误、取消和全局预算不足仍会中止调查，不能按可选服务故障忽略。

分支输出保存结论、支持证据、冲突、未知项与停止原因。未完成项和冲突进入主调查，风险输出强制保留这些缺口。关键分支标记`required`后，未完成会请求人工补证；非关键分支可以带缺口继续。用户确认观察并恢复原调查时，各子问题按新补证轮次重新取证，旧分支记录保留。

## 5.2 专业技能与执行预算

[技能目录](../app/modules/operation_event/skills)包含阀门泄漏调查、重复隐患复盘、规范变更复核。每个`SKILL.md`使用Agent Skills的名称、描述和`metadata.version`格式，正文包含检查步骤、必查材料与输出要求。协调者先看摘要，再加载命中正文；运行冻结文件哈希，排队期间文件被替换会拒绝静默混用版本。服务端只允许仓库内的三个技能，不执行任意脚本。

调查接口可提交`skills`、`max_parallel`、`max_branch_steps`、`branch_timeout_seconds`、`max_model_calls`、`max_tool_calls`、`max_tokens`、`context_chars`与可选`max_cost_microusd`。调用数覆盖全部角色与分支，恢复不重置预算。每次模型请求按输入字节保守估算并限制输出，结束后记录实际用量。并发请求在发送前通过数据库锁预留各自最坏Token和费用，避免重复使用同一份剩余额度；用量缺失时保留保守预算估计。费用上限要求在`event-classification`模型别名的`config.pricing_microusd_per_million`登记正的`input/output`价格；未配置的费用是未知，不能解释成免费。RAG查询改写的文字模型调用也纳入同一模型次数、Token与费用预算；本地嵌入和排序受知识服务配置约束。

## 5.3 工具取证与RAG

ReAct可以理解为“决定下一步→执行工具→观察结果→继续判断”。模型只返回允许的工具名和普通查询参数；服务端执行白名单函数、检查权限并保存证据。模型不持有数据库连接，也不能拼接任意SQL或Cypher。

内部工具包括历史事件、工单、交接记录、`search_knowledge`、`search_experiences`以及三个业务图谱工具、实测验收核查和已保存证据分块读取。RAG在`search_knowledge`中被调用，返回已发布且有效的原文、版本和定位，模型据此说明处置依据。

检索到经验后还要比较设备、现象和适用前提。被排除的经验不能继续混入风险与方案证据集；历史成功也不能证明本次处置已经有效。

## 5.4 运行状态与角色证据

`AgentRun`保存固定事件版本、状态、配置快照和总用量；`AgentTask`保存角色任务；步骤记录模型或工具操作；`AgentEvidence`保存来源、版本、内容摘要与权限范围。

LangGraph检查点保存运行状态，支持中断后恢复。同一次运行恢复与发起新的调查是不同操作。恢复前仍须核对当前来源、权限和租约；过期检查点不是永久有效的业务事实。

实现入口为[investigation.py](../app/modules/operation_event/application/investigation.py)，工具白名单为[investigation_tools.py](../app/modules/operation_event/application/investigation_tools.py)。预算、取消、输出Schema与证据引用都由代码执行约束，提示词只承担其中一部分。

风险角色读取可用事实；方案角色结合风险与适用规范；复核角色重新对照原始证据。大正文保存在`AgentEvidence`，上下文显示ID、来源、版本、哈希和摘要，需要全文时调用`read_investigation_evidence`，参数为`证据UUID:起始字符偏移`，每块最多6000字符。回查仍验证当前权限和来源版本。摘要不是额外事实。

气象与空间结果按操作及站场选择保留当前快照。同一范围重新查询后，角色只使用较新的记录；过期记录保留作历史，补证后重新取证，不把它与新结果混用。离线提示词重放按原调查完成时刻解释时效。

## 5.5 人工补证与继续调查

关键事实缺失时，调查保存问题并进入`waiting_input`，Worker结束本次执行。人员提交观察并确认后，恢复接口核对事件版本和请求轮次，通过原Job继续调查。已消耗预算和历史证据保留，下游判断按新事实重做；有时效的外部材料重新查询。

[第12章](第12章_持续调查与经验记忆.md)说明观察、检查点与恢复的具体关系；MCP Tasks使用同一恢复服务。

## 5.6 MCP协议与工具

MCP约定外部AI应用怎样发现工具、读取资源和取得提示模板。工具是可执行业务能力，资源是可读取上下文，提示模板是供客户端使用的任务说明。MCP不决定模型何时行动，也不替代后端授权。

项目在`/mcp/`提供Streamable HTTP服务。每次调用验证Bearer身份，再从数据库加载当前授权。内部调查直接调用进程内工具，外部客户端使用MCP协议；两者复用应用服务。

| 工具 | 主要参数 | 返回或行为 |
|---|---|---|
| `search_events` | `event_id, query` | 同组织可见的正式历史事件 |
| `search_work_orders` | `event_id, query` | 可见工单 |
| `search_handover` | `event_id, query` | 可见交接记录 |
| `get_case_context` | `event_id` | 当前事件、已确认观察和候选摘要 |
| `search_knowledge` | `event_id, query` | 已发布有效知识及定位 |
| `search_experiences` | `event_id, query` | 审核有效的同组织经验 |
| `get_evaluation_improvement` | `improvement_id` | 参与者有权读取的改进记录 |
| `trace_case_relations` | `event_id` | 业务证据路径 |
| `find_recurrent_hazards` | `event_id` | 人工确认设备故障的重复异常 |
| `assess_change_impact` | `event_id` | 当前事件引用知识的变更影响 |
| `get_work_order_verification` | `work_order_id` | 措施、前后读数和独立验收历史 |
| `get_impact_review` | `review_id` | 变更复核及当前目标修订 |
| `submit_case_observation` | `event_id, expected_version_id, content, request_id` | 提交待人工确认的观察 |
| `get_weather_alerts` | `event_id, station_id?` | 关联站场当前预警及有效期 |

| `start_investigation` | `event_id, request_id, options?` | 创建持久调查任务 |

服务提供16个读取工具，以及提交待确认观察、创建调查任务两个受限写入入口。内部Evidence角色仍只注册只读工具，不通过模型调用自行确认观察或批准工单。

## 5.7 观察提交与幂等

外部助手提交内容时必须提供当前事件版本和UUID类型的`request_id`。服务端在事件锁保护下，以用户、事件和请求编号确定观察记录。同一请求的相同内容和版本重放，返回同一条记录；复用编号提交不同材料会冲突。

新观察为`pending`，不进入事实上下文。人员通过观察审核接口确认后，才可被后续调查当作事实。重试仍检查当前编辑权限，已经确认或撤回的原观察返回其当前状态，不偷偷创建新副本。

MCP不走通用HTTP响应幂等缓存，避免业务或权限变化后重放旧内容。去重在业务事务中完成，实现见[mcp_operations.py](../app/modules/operation_event/application/mcp_operations.py)与[memory.py](../app/modules/operation_event/application/memory.py)。

## 5.9 MCP任务状态

依据[2026-07-28 Tasks扩展](https://github.com/modelcontextprotocol/ext-tasks/blob/main/specification/2026-07-28/tasks.md)，客户端每次请求的`_meta.io.modelcontextprotocol/clientCapabilities.extensions`须包含`io.modelcontextprotocol/tasks: {}`。未协商的客户端不能取得任务句柄，返回`-32021`。

`tools/call`调用`start_investigation`返回扁平的`{resultType:"task", taskId, status, createdAt, lastUpdatedAt, ttlMs, pollIntervalMs}`。返回前调查与事务Outbox已经落库，关闭HTTP连接不会取消任务。任务ID对应同一`AgentRun`，原发起人可查；同一`request_id`和相同参数重复调用返回同一任务，不同参数冲突。

| 方法 | 参数 | 结果 |
|---|---|---|
| `tasks/get` | `taskId` | `resultType:complete`及任务详情；终态内嵌工具结果 |
| `tasks/update` | `taskId,inputResponses` | 提交人工补证结果后恢复原任务 |
| `tasks/cancel` | `taskId` | 协作取消，确认结果为`resultType:complete` |

HTTP路由头`Mcp-Name`应设为`taskId`。状态为`working/input_required/completed/cancelled`；业务执行失败按工具错误完成，`isError:true`。任务不在内存保活，不提供旧版的`tasks/list`或`tasks/result`。采用轮询，不实现可选订阅通知。

缺证时`tasks/get.inputRequests`包含一个`elicitation/create`表单，键为本轮`request_version`。客户端提交`inputResponses[键]={action:"accept",content:{confirmed_observation_ids:"UUID1,UUID2",reason:"核实说明"}}`。只能引用新建且已由人工确认的当前事件观察；直接写一段回复不能成为事实。旧轮次和已回答的键忽略；decline/cancel请求取消调查。

相关REST入口：`GET /api/v1/investigation-skills`、`GET /api/v1/agent-runs/{run_id}/input-request`、`POST /api/v1/agent-runs/{run_id}:resume`。完整协议及端到端用例见[test_investigation_extensions.py](../tests/test_investigation_extensions.py)。

## 5.10 气象与空间取证

`get_weather_alerts`、`get_map_context`、`query_enterprise_gis`、`get_access_route`沿人工设备关联和站场位置查询。协调者按现场需要选择环境分支，来源、有效期和位置版本进入原证据链。坐标、配置与使用方法先读[第14章](第14章_气象预警与GIS地图工具.md)。

## 5.11 工单执行与验收

```text
draft → pending_review → approved → dispatched → in_progress → resolved → closed
                 ↓                                      ↑          ↓
                draft                                   └──驳回─────┘
```

允许的非终态还可按规则取消，`closed`和`cancelled`为终态。各动作提交当前`expected_version`和理由。工作流审核产生草稿，不等于工单已经审核、派发或开始执行。

整改提交必须包含`action`、`result`和结构化`measurements`。测量记录包含指标、单位、前值、后值、判定依据、阈值与测量时间；不能只写“已处理”。附件须先完成服务端验证。

独立验收引用当前整改记录，验收人不能是整改提交人或工单执行人；需要提交本次核验读数，标准须与整改记录一致。通过后关闭，驳回后回到执行状态并保留原整改、验收和后续重做记录。
