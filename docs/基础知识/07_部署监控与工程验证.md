## 35 Docker、Compose、镜像、容器、网络与数据卷

镜像是程序和运行依赖的构建产物；容器是镜像启动后的进程环境。停止或替换容器不等于删除外部数据卷。卷保存需要跨容器保留的数据，例如PostgreSQL和对象存储文件。

Compose用配置文件描述多个服务、环境、网络、卷与启动关系。本项目API、Worker和Beat可使用同一后端镜像、不同启动命令；数据库、消息服务、模型与监控各有项目服务。

容器中的`localhost`指向该容器自己。容器间通过项目网络和服务名通信，例如后端访问`postgres:5432`；电脑通过发布端口访问时才使用主机地址。把主机端口直接照搬进容器配置，常会连错目标。

**基本用法。**

```bash
python3 scripts/manage_stack.py up
python3 scripts/manage_stack.py status
python3 scripts/manage_stack.py logs
python3 scripts/manage_stack.py down
```

`down`按当前工具约定保留数据卷；重建数据的`reset`是不同操作，不作为入门练习执行。首次启动可能需要依赖和模型下载；`--offline`源码更新要求本地运行镜像的依赖锁匹配，不能跳过检查强称离线可用。

健康检查分别检查进程、依赖或组件就绪，不等于模型效果合格。CPU大模型还受内存、线程与并发限制；主后端Python 3.14和CPU模型服务Python 3.13是有意分开的运行环境。

看[Compose](../../infra/compose/project.yml)、[启动工具](../../scripts/manage_stack.py)与[基础设施说明](../../infra/README.md)。

## 36 Prometheus、Alertmanager与Blackbox Exporter

监控指标是随时间变化的数值。Prometheus定期拉取指标并保存时间序列，规则判断是否满足告警条件；Alertmanager接收告警并处理分组、抑制和通知路由。Blackbox Exporter从外部探测目标，例如HTTP是否可达。

标签用来区分指标维度。将用户ID、事件UUID等无穷增长的值直接做标签，会产生大量时间序列；项目使用受限的状态等统计维度。Counter适合累计次数，Gauge适合当前数量，Histogram适合分桶分布；本项目实际暴露内容应以实现为准，不能假定三种都已提供。

```text
API暴露指标 → Prometheus定期抓取 → 告警规则
HTTP外部探测 → Blackbox Exporter ────────┘
告警状态 → Alertmanager处理与路由
```

**基本使用。** 先检查`/health/live`、`/health/ready`和`/health/knowledge`的区别，再在有权使用的监控配置下查看`/metrics`。指标入口使用项目的运维认证配置，不要把Bearer或监控令牌写进示例。

指标适合发现趋势和异常，具体业务失败还需看Job事件、审计和日志。配置见[monitoring](../../infra/monitoring)，实现见[operations.py](../../app/shared/platform/operations.py)。

## 37 pytest、异步测试、TestClient、Fake/Mock与覆盖率

测试把预期行为写成可重复执行的检查。pytest发现测试函数并提供fixture管理准备与清理；pytest-asyncio支持异步测试；FastAPI TestClient在测试进程内驱动ASGI应用，不要求另开浏览器。

本项目部分协议测试使用httpx2相关测试客户端能力，外部HTTP适配器则使用httpx；不要把相近名称当作可以任意互换的导入。Fake提供完整但合成的能力实现，Mock控制指定调用、返回值或错误；二者的成功不代表真实模型或第三方API已经联通。

```python
def test_ratio():
    relevant = {"A", "B"}
    returned = {"B", "X"}
    assert len(relevant & returned) / len(returned) == 0.5
```

这个最小测试用`assert`表达预期，失败时应定位差异，而不是把断言改成迎合错误实现。项目测试还覆盖权限、状态、并发、来源变化及外部协议。

**基本命令。** 确认专用测试库配置后：

```bash
uv run pytest tests/test_site_context.py
uv run coverage run -m pytest
uv run coverage report
```

行覆盖率说明哪些代码被执行；分支覆盖率进一步统计条件的不同出口。高覆盖率不能保证断言正确，也不能替代代表性业务样本。真实检索与模型测试按配置启用，报告要保留哪些被跳过。

准备方式见[conftest.py](../../tests/conftest.py)，测试目录见[tests](../../tests)。该fixture会删除并重建目标测试库的`public` Schema，不能让`TEST_DATABASE_URL`指向业务库。

## 38 Ruff、mypy、compileall与架构边界检查

格式化保持代码排版一致；lint发现常见错误与可疑用法；类型检查比较声明与调用是否兼容；编译检查发现语法等问题。它们检查不同层面，任何一种通过都不表示业务逻辑已经正确。

Ruff负责本项目格式和lint；mypy结合类型声明检查参数与返回值；`compileall`编译源码。架构测试还检查业务模块不要绕过端口直接依赖数据库之外的搜索SDK或出站适配器。

**基本用法。**

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy app scripts dev
uv run python -m compileall -q app alembic tests scripts dev services
```

`format --check`只报告格式差异，去掉`--check`会改写文件。`compileall`可能生成字节码缓存，但不启动业务服务。类型提示不足的代码依然可能有运行时错误，因此继续保留针对实际行为的测试。

规则见[pyproject.toml](../../pyproject.toml)，分层约束见[test_architecture.py](../../tests/test_architecture.py)。阅读错误时优先修正实际问题，不要一律添加忽略标记。

## 39 uv、锁文件、Hatchling、约束、依赖审计与模型revision

声明依赖与锁定环境是两个步骤。`pyproject.toml`声明项目要求，`uv.lock`记录解析后的依赖树；`uv sync --frozen`按现有锁恢复，不在执行时重新随意选择版本。Hatchling是项目构建wheel等安装产物使用的后端，不是服务进程。

独立模型服务使用`requirements.txt`和`constraints.txt`：前者列出安装要求，后者限制解析时可选版本。约束文件不会因为出现一个包名就自动安装该包。后端开发依赖和生产依赖也分组管理，避免把所有测试工具带进运行镜像。

```bash
uv lock --check
uv sync --frozen
uv run pip-audit --local --skip-editable
```

审计检查已知依赖漏洞及环境信息，不证明业务授权或模型输出安全。实际变更依赖后还需重建相应镜像并验证兼容性，不能只改一个版本字符串。

模型revision标识具体权重修订，和Python包版本不同。Embedding权重、分词或维度改变，可能要求重新索引；视觉、语音权重变化也会影响结果。项目锁定相关revision，使运行更可复核。

入口：[pyproject.toml](../../pyproject.toml)、[uv.lock](../../uv.lock)、[services](../../services)及[离线构建工具](../../scripts/build_offline.py)。

## 40 Git、GitHub Actions、CI、备份与恢复

Git记录代码快照，工作区、暂存区和提交是不同状态。分支是提交历史中的引用，远端仓库用于同步协作。代码提交不包含运行数据库与对象文件的完整备份。

GitHub Actions按工作流执行自动化步骤。CI在提交或PR等事件上运行检查，帮助发现格式、类型、测试和迁移问题；CI通过只说明这些检查通过，不等于真实生产效果验收。

**先学只读观察。**

```bash
git status --short
git diff --stat
git log --oneline -5
```

随后理解`git add`将选定变化放进暂存区、`git commit`记录暂存快照。重写已共享历史会影响协作，本篇不把历史重写或删除备份作为练习命令。

备份要覆盖数据库、对象、必要配置和版本信息；恢复演练则验证备份真的能读、能查询、能重新构建索引。只看“备份文件存在”不足以证明可恢复。数据库记录与对象若来自不同时间点，还可能互相引用缺失。

项目CI见[工作流](../../.github/workflows/ci.yml)，备份与隔离恢复见[backup_stack.py](../../scripts/backup_stack.py)。先读脚本参数和[基础设施说明](../../infra/README.md)，不在正式库直接试恢复。

## 41 UTC、业务时区、定时任务、版本快照、哈希与审计链

UTC用于表达统一时刻，业务日期则依赖所在时区。例如北京时间2026-11-10零点对应UTC前一天16点。tzdata提供时区规则数据；`Asia/Shanghai`是时区标识，不只是界面显示文字。

```python
from datetime import date, datetime, time, UTC
from zoneinfo import ZoneInfo

local_start = datetime.combine(date(2026, 11, 10), time.min, ZoneInfo("Asia/Shanghai"))
utc_start = local_start.astimezone(UTC)
assert utc_start.isoformat() == "2026-11-09T16:00:00+00:00"
```

`2026-11-10`只是日期，不是一个完整时刻。带时区的datetime说明该时刻如何解释；不带时区的值不能靠猜测当作UTC，项目跨服务时间使用带时区值。这个例子说明为什么日报不能直接按UTC零点截一天。周期调度还要区分Beat自身时区和报告业务时区；系统按计划生成草稿，不会自动替代人工发布。

版本快照记录一次执行具体用了哪份资料、模型和配置。内容哈希把内容映射为摘要，用来发现变化；哈希不是加密，也不能证明原始内容真实。审计链将上一条摘要纳入下一条摘要计算，使记录顺序与变化可检查。

```text
第1条：本条内容 → 摘要H1
第2条：本条内容 + H1 → 摘要H2
第3条：本条内容 + H2 → 摘要H3
```

若拥有足够数据库控制权的人能重算整条链，仅靠链本身不能阻止所有篡改；还需要权限、备份和外部保留等管理措施。项目审计链提供可复核关联，不能宣称是不可篡改区块链。

**基本使用。** 核对报告时同时查看业务日期和时区；核对调查时查看事件版本、观察修订、配置快照及证据摘要。实现见[报告服务](../../app/modules/report/application/service.py)、[Beat配置](../../app/bootstrap/celery_app.py)和[审计写入](../../app/shared/platform/service.py)。
