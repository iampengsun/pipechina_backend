# 第2章：公共基座、启动与测试

FastAPI把HTTP请求交给函数；Pydantic检查输入结构；SQLAlchemy的Session组织一次数据库操作；事务让关联变化一起提交或撤销。Celery执行后台任务，RabbitMQ交付消息，Redis保存短期共享状态。它们各自成功并不能证明整条业务链已完成。

相关基础：[Web与配置](基础知识/01_Web接口与配置.md#t02)、[会话与事务](基础知识/02_数据库事务与迁移.md#t04)、[迁移](基础知识/02_数据库事务与迁移.md#t07)、[Celery](基础知识/03_任务权限与文件存储.md#t08)、[RabbitMQ](基础知识/03_任务权限与文件存储.md#t09)、[Redis](基础知识/03_任务权限与文件存储.md#t10)、[Outbox与租约](基础知识/03_任务权限与文件存储.md#t11)、[认证与权限](基础知识/03_任务权限与文件存储.md#t12)、[容器](基础知识/07_部署监控与工程验证.md#t35)、[测试与工具链](基础知识/07_部署监控与工程验证.md#t37)。 测试会重建专用测试库，必须与业务库分离。

## 2.1 从配置到一键启动

安装Python 3.14、uv和Docker，给完整CPU模型栈至少16GB Docker内存。首次启动需要下载依赖和模型权重；文字模型调用仍需网络。

```bash
uv sync --frozen
python3 scripts/manage_stack.py up
```

启动工具会检查配置与容量。若提示缺少文字模型密钥，在项目`.env`中填写`DASHSCOPE_API_KEY`后再次启动，保留北京地域配置。`.env.example`描述配置项；不要将真实密钥写入文档或提交。

完整Compose有20项服务：包括API、业务Worker、维护Worker、Beat、模型服务、数据服务、监控和两个一次性初始化任务。容器、网络、数据卷归项目管理；初始化任务退出码为0属于正常结果。

```bash
python3 scripts/manage_stack.py status
python3 scripts/manage_stack.py logs
python3 scripts/manage_stack.py down
```

`down`保留数据卷。`reset`会删除项目卷，只有明确需要重建全部项目数据时使用。离线源码更新使用`up --offline`，前提是本机运行镜像中的依赖锁与当前文件完全一致。

## 2.2 数据库会话与事务

Engine管理数据库连接，Session管理一次业务交互中的查询和待写对象。`flush`把变化送入当前事务并取得主键，`commit`提交，`rollback`撤销。Session不是数据库本身，也不应在多个并发任务间共享。

```python
async with database.session_factory() as session:
    session.add(record)
    await session.flush()
    # 在同一事务内保存相关记录、审计或Outbox。
    await session.commit()
```

上面是事务形状的示意，`record`须替换为实际领域对象。实现见[db.py](../app/shared/db.py)和[公共业务服务](../app/shared/platform/service.py)。关联记录必须在同一事务中满足外键、唯一性和业务条件，不能仅依赖请求前的存在性查询。

并发修改有两道常见控制：行锁避免同一关键操作交错；`expected_version`避免旧页面覆盖新结果。发生409后应重新读取资源，核对版本与状态，再决定是否提交新操作。

## 2.3 初始基线与顺序升级

`alembic/versions/0001_initial_schema.py`包含83张应用表、索引、约束、图谱变更触发器和检查点Schema。后续`0002_agent_tasks`增加提示词搜索记录、任务等待输入状态及活动任务唯一索引，`0003_station_locations`增加带版本的站场位置；当前共85张应用表。已有`0001`库直接升级，不重建数据。新库执行：

```bash
uv run alembic upgrade head
uv run python scripts/verify_postgres_schema.py
uv run alembic check
```

`upgrade`执行结构变更；结构核对检查应用表和版本；`check`比较模型与数据库是否还有未记录的结构差异。首版还对循环引用外键作显式处理，不能把多个迁移文件简单拼接后就认为新库可用。

原0007环境已经包含完整结构时，先备份，再执行：

```bash
uv run python -m scripts.adopt_initial_schema
uv run python -m scripts.adopt_initial_schema --apply
```

该工具比较结构、图谱触发器和已有版本，符合条件后只修改迁移标记。其他历史或不完整数据库会拒绝采用首版标记。`downgrade base`会删除应用结构及检查点Schema，只应在可丢弃环境练习。

## 2.4 身份、权限和数据范围

JWT是签名身份凭据。API先验证签名、有效期、签发方和受众，再加载本地用户、组织与角色授权。权限如`event:read`表示能做什么；数据范围表示能对哪些记录做，例如本人、本组织或全局。

会议、知识源和经验还会检查来源ACL。把记录ID写进旧摘要，不会获得永久读取权。异步任务执行时和重要结果提交前也重新加载权限，防止排队期间撤权后继续发布。

本机Mock IdP只用于开发。需要调试接口时，通过本机`http://127.0.0.1:9001/token`取得令牌，然后在请求头使用`Authorization: Bearer <token>`。正式部署须使用实际身份服务；角色、分派和管理接口见本章接口表。

## 2.5 RabbitMQ基础

RabbitMQ是消息代理。生产者发送消息，消息经交换机和路由进入队列，消费者从队列接收并处理。Celery是生产者/消费者使用的任务框架，RabbitMQ负责传输，不执行Python业务函数。

| 概念 | 含义 | 排障时看什么 |
|---|---|---|
| Queue | 等待消费的消息队列 | 有没有消费者、积压多少 |
| Ready | 尚未交付的消息 | 路由或Worker是否正确 |
| Unacked | 已交付但未确认的消息 | 长任务、阻塞或消费者异常 |
| ACK | 消费者确认处理完成 | 提前确认可能丢失恢复机会 |
| 重投 | 未确认消息重新交付 | 业务必须能处理重复执行 |

交换机（Exchange）接收生产者发布，根据路由键（routing key）与绑定规则选择队列；队列再交付给消费者。本项目由Celery声明和使用这些关系，例如调查任务路由到`ai_text`，不是API直接执行一段排队中的Python代码。

还要区分两种确认：Publisher Confirm告诉生产者消息已被代理接受，消费者ACK表示处理交付完成。前者不能证明业务已经成功，后者也不能替代数据库中的完成状态。持久队列、消息持久化和发布确认帮助故障恢复，事务Outbox与业务幂等继续处理跨系统窗口和重复交付。

开发管理入口为`http://127.0.0.1:15672`，使用项目RabbitMQ配置登录。管理界面的队列消息数量不等于业务完成数量，最终结果仍以PostgreSQL中的Job和业务记录为准。

可用只读命令观察项目队列：

```bash
docker compose --env-file .env -f infra/compose/project.yml exec rabbitmq \
  rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
```

提交一个异步业务请求后，同时观察Job状态、队列和Worker日志。任务可能很快消费，某一刻队列为空不能证明从未投递。不要为观察而清空队列或删除生产消息。

## 2.6 Outbox、Worker与Beat

如果业务先提交数据库，再发送消息，进程可能在中间退出。Outbox把业务记录、Job和待发消息写入同一数据库事务，提交后由发布器投递；失败会保留状态并按规则重试。

Beat负责按时间表投递周期任务，Worker负责执行。维护Worker只消费`maintenance`队列，承担Outbox、超时维护和提醒；业务Worker消费音频、视觉、调查、报告和知识队列。图谱同步使用`knowledge_index`队列，周期投递间隔30秒，实际执行可能因排队延后。

Celery采用晚确认、Worker丢失后重投及预取限制。消息可能重复到达，所以业务还需要租约、资源版本、幂等和提交前检查。外部模型调用本身无法由数据库事务保证恰好执行一次。

## 2.7 Job、幂等与租约

Job常见状态为`queued`、`running`、`succeeded`、`failed`、`cancelled`。HTTP 202只代表受理；应根据返回的Job ID读取结果及事件历史。重试通过正常接口创建新尝试并更新当前绑定，不直接把failed改成succeeded。

租约给一次执行分配令牌与有效期。重投、超时或旧Worker恢复时，令牌检查阻止旧尝试覆盖新结果。取消通常在检查点生效，不能保证已经发出的远程推理立即停止。

普通JSON写请求可使用`Idempotency-Key`减少重复提交。知识请求和MCP依赖实时权限，不走通用响应重放；MCP观察使用业务事务内的`request_id`去重。幂等只解决约定范围内的重复，不代替鉴权、版本检查或唯一约束。

## 2.8 对象上传与验证

上传分为申请、传输、完成验证。申请接口给出对象键和授权；客户端将字节传到存储后调用完成接口。服务端核对对象、大小、类型、校验值及授权有效期，验证通过才允许转写、分析或引用附件。

因此“客户端说传完了”与“文件已验证”是不同状态。共享附件实现见[uploads.py](../app/shared/media/uploads.py)，工单和隐患使用相同验证规则。

## 2.9 测试与运行验证

配置独立、可丢弃的`TEST_DATABASE_URL`，数据库用户与连接方式可参考测试配置。测试会删除目标库的`public` Schema，不能指向业务库。

```bash
uv run ruff check app scripts dev tests
uv run ruff format --check app scripts dev tests
uv run mypy app scripts dev
uv run pytest
RAG_EXTERNAL_TEST=1 uv run pytest tests/test_knowledge_external.py
```

默认回归中的Fake Provider验证业务规则和失败路径；外部索引测试显式连接真实服务，使用隔离数据。真实本地模型与Qwen分别受`RAG_MODELS_TEST`、`RAG_LLM_TEST`开关控制，后者会产生实际模型调用。

本机合成业务验证可运行`uv run python -m scripts.accept_business_graph`。备份、恢复演练、生产配置和运行告警分别见[基础设施说明](../infra/README.md)、[备份脚本](../scripts/backup_stack.py)和[恢复演练](../scripts/restore_probe.py)。健康检查通过仍须结合任务消费、业务状态和实测结果判断链路是否完成。
