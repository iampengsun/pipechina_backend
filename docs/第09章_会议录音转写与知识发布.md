# 第9章：会议转写、纪要与知识发布

语音识别输出文字，说话人分离输出匿名声音标签，人工姓名映射才说明标签对应谁。来源ACL决定哪些会议资料可被读取；知识发布把审核后的会议材料纳入可检索资料，不会将未确认纪要自动作为规范事实。

相关基础：[语音、时间片段与说话人](基础知识/05_检索文档与多模态.md#t30)、[权限与来源范围](基础知识/03_任务权限与文件存储.md#t13)、[RAG发布与取证](基础知识/05_检索文档与多模态.md#t23)、[异步任务](基础知识/03_任务权限与文件存储.md#t11)。

## 9.1 会议资料的三层结果

会议录音保留原始输入，转写版本保留发言文字和时间，纪要版本整理摘要、决定、行动项与未知问题。模型纪要是草稿；人员校订和确认后，才能作为后续知识发布的来源。

说话人分离返回标签，真实参会人由`participant_key`标识。将`speaker_label`绑定到参会人是人工身份操作，不能仅凭声音标签自动认定姓名。录音中多说话人重叠、噪声或片段缺失都应在校订中处理。

## 9.2 完整流程

```text
登记会议及参会人 → 申请并验证录音上传 → 转写
→ 人工校订片段 → 绑定说话人 → 生成纪要草稿
→ 编辑与确认纪要 → 发布到知识处理流程 → 审核发布知识
```

会议创建包含带时区的起止时间、录音信息、参会人和`reader_ids`。结束时间须晚于开始时间，参会人key不能重复。上传与转写均按第2章的对象验证和异步任务规则执行。

## 9.3 转写和纪要版本

转写保存全文及按时间排序、不重叠的片段。人工修改产生新版本，不覆盖旧文字。说话人映射绑定现有标签与参会人，不能建立指向不存在对象的映射。

纪要结构包含`summary`、`decisions`、`action_items`和`unknowns`。行动项可以记录任务、负责人和期限，缺失时保留未知，不能让模型补造未发生的决定。修改转写后须核对纪要来源，旧纪要不会自动代表新文字。

## 9.4 发布到知识库

发布操作关联已确认纪要、目标知识库、文档和知识版本，保存`MeetingKnowledgePublication`。文字中的时间标记帮助读者追溯原始发言，但当前并未提供精确音频片段回听API。

会议API调用知识应用层的统一Job入口，不从一个API控制器调用另一个控制器。之后的解析、索引、审核和发布遵循第8章流程，不因来源是会议而绕过发布门槛。

## 9.5 来源ACL与录音保留

会议读取权限与`reader_ids`共同约束内容。会议生成的知识即使进入知识库，查询、引用与旧运行读取仍检查会议来源ACL，不能通过发布文档扩大原资料的读取范围。

录音删除记录原因及删除过程，先检查相关知识发布状态等约束，再清理对象。删除文件与删除会议正文不是同一操作，历史纪要、发布关联和审计仍按规则保留。周期清理遵守配置的保留策略，不应手动删对象后把数据库当作仍可用。

## 9.6 代码与验证

[schemas.py](../app/modules/meeting/domain/schemas.py)解释参会人、片段与纪要结构；[service.py](../app/modules/meeting/application/service.py)实现版本、ACL、说话人绑定、发布及删除规则；[API](../app/modules/meeting/api/router.py)负责请求边界。

[会议测试](../tests/test_meeting_flow.py)验证主流程及来源权限。练习应包含转写修改后旧纪要、同一会议重复发布、撤销读者后检索旧知识、录音删除与发布并发、以及任务取消后提交等场景。
