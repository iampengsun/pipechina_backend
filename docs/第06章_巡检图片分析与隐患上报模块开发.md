# 第6章：巡检图片分析与隐患上报

视觉语言模型同时读取图像和文字，产生候选观察。MiniCPM-V是模型，Transformers和PyTorch负责加载及推理，Pillow负责图像处理；JSON约束和Pydantic只能检查输出形状，不能证明看图判断正确。

相关基础：[视觉模型与运行组件](基础知识/05_检索文档与多模态.md#t31)、[输出校验](基础知识/01_Web接口与配置.md#t03)、[图片上传](基础知识/03_任务权限与文件存储.md#t14)、[人工效果验收](基础知识/06_效果评测与验收.md#t34)。

## 6.1 图片分析为什么先产生候选

视觉模型可以描述图片、识别可疑现象并给出位置，但图片可能缺少比例、时间、设备状态或现场背景。项目将模型结果保存为巡检发现候选，人员核对后再关联事件或登记隐患。

巡检记录描述一次检查，图片是输入附件，发现是分析结果。一次检查可有多张图片和多条发现；“没有发现候选”也是合法结果，不能为了凑输出自动生成隐患。

## 6.2 数据与流程

| 对象 | 保存内容 |
|---|---|
| `InspectionRecord` | 站场、管线、设备文字描述、检查时间与备注 |
| `InspectionImage` | 对象存储位置、文件信息、验证状态 |
| 分析运行 | 当前任务、状态与本次模型结果 |
| `InspectionFinding` | 可疑现象、证据和人工复核状态 |
| 关联记录 | 发现与事件、隐患或调查的衔接 |

```text
建立巡检记录 → 申请图片上传 → 传输并验证 → 提交分析
→ 保存候选 → 人工确认/驳回 → 受控关联事件或登记隐患
```

图中的设备名称是来源描述；需要跨事件按同一设备统计时，另用第13章的人工设备ID关联，不能只凭名称相近自动合并。

## 6.3 创建与上传

巡检记录请求示例：

```json
{
  "station_name": "教学输气站",
  "equipment_name": "二号阀门",
  "inspected_at": "2026-11-10T09:00:00+08:00",
  "notes": "合成软件练习记录"
}
```

图片申请提交真实文件名、类型、大小及可选SHA-256。按返回授权传输后，调用完成接口。服务端验证实际对象，分析只使用已验证图片。上传登记不能代替传输，分析错误也不能通过把图片状态手改为verified解决。

## 6.4 分析任务与重复执行

API保存Job和Outbox，Worker通过视觉端口调用服务，结构化结果经Schema校验后落库。统一租约控制重复投递和超时尝试；旧任务提交时检查当前绑定，避免覆盖后发任务。

模型结果引用所属巡检和图片。客户端根据本次Job与运行结果定位产物，不使用“最新发现”推断是哪次任务产生的。任务失败先检查对象验证、视觉服务、输出格式与执行日志，再通过正常重试恢复。

## 6.5 人工复核与关联

确认或驳回发现需要理由。确认解决的是“这一条图片候选是否被业务人员接受”，不会自动证明风险等级、现场真实原因或处置有效性。

关联已有事件时检查事件存在、状态与访问范围；创建正式业务产物也通过应用服务执行。撤销关联保留理由和历史，不删除原图片或候选。进入隐患流程后，评估、整改和验收继续使用隐患模块规则。
