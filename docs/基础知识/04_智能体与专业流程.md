# 智能体、专业技能、记忆与提示词优化基础

本篇对应16—22。统一用“阀门渗漏调查”举例：系统需要取得事实、查询规范、评估风险、形成建议，并在缺证时等待人工确认。不同技术负责其中不同问题。

## 16 LangGraph、StateGraph、Checkpoint与人工恢复

LangGraph把工作流表示为状态图：节点执行一段操作，边规定下一步，状态保存节点之间共享的数据。条件边根据结果选择后续节点。它帮助组织流程，业务是否允许执行仍由应用服务决定。

下面是可独立理解的最小图，`TypedDict`这里只用来声明状态形状：

```python
from typing import TypedDict
from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    question: str
    checked: bool


def inspect(state: State):
    return {"checked": bool(state["question"].strip())}


builder = StateGraph(State)
builder.add_node("inspect", inspect)
builder.add_edge(START, "inspect")
builder.add_edge("inspect", END)
graph = builder.compile()
assert graph.invoke({"question": "检查阀门", "checked": False})["checked"]
```

节点返回需要更新的字段，图合并状态；`compile`生成可运行图。Checkpoint是持久化的执行位置和状态，方便进程重启或人工补证后恢复。Postgres Saver把检查点保存在PostgreSQL；它不是业务事实库的替代品。

`interrupt`暂停图并把问题交给外部；恢复时使用`Command(resume=...)`。恢复可能从中断节点的开头重新执行，因此节点中中断前的副作用必须幂等，不能重复创建工单或发消息。

**在本项目中。** [investigation.py](../../app/modules/operation_event/application/investigation.py)组织图，[input_requests.py](../../app/modules/operation_event/application/input_requests.py)验证人工确认记录后恢复原Job与AgentRun。恢复不重置预算，也不取消事件版本与权限检查。详见[第12章](../第12章_持续调查与经验记忆.md)。

## 17 ReAct、多角色智能体、动态子调查与预算

智能体在本项目中是能根据当前材料决定下一步工具操作的程序。ReAct可以按“决定行动 → 调用工具 → 观察结果 → 再判断”来理解。模型提出动作与参数，服务端从白名单执行；模型不直接拼SQL或获得数据库连接。

```text
问题：异常是否反复出现？
动作：find_recurrent_hazards
观察：同设备同故障的已确认记录、措施及实测
判断：是否需要补证；结论保留依据和未知项
```

多角色把任务分成协调、取证、经验适用性、风险、方案和复核。它们可以共用同一个文字模型，区别在输入、目标和输出契约。模型复核仍属于模型判断，不是独立专家验收。

动态任务图让协调者按本次问题选择子调查。例如规范适用性与历史复发可以独立取证后汇总；两项之间有依赖时不能仅为加速而并行。并发表示多个IO任务可以交错等待，不等于自动获得多个CPU核心。`TaskGroup`管理一组异步子任务的生命周期；`Semaphore`限制同时准入的任务数。它们不管理数据库事务，因此每个分支仍需自己的Session和统一的提交检查。

**基本用法。** 调查接口可提供上限，例如：

```json
{"max_parallel": 2, "max_branch_steps": 4, "branch_timeout_seconds": 90, "max_model_calls": 40, "max_tool_calls": 20, "max_tokens": 60000}
```

子调查先执行初始查询，再由模型检查证据是否满足完成条件。历史事件查询可继续追查工单和实测，规范问题可继续核查知识变更；工具范围按子问题限定。完成时给出结论、支持证据、冲突和未知项；缺现场事实时向已有人工补证流程提交问题。

上限约束整次调查，不能让每个分支都重新获得一整份预算。并发分支使用独立Session；共享Token与费用额度通过数据库预留，调用结束再结算。达到上限应明确结束或报出不足，不能悄悄丢掉证据后宣称完成。

看[分支执行](../../app/modules/operation_event/application/subinvestigations.py)、[预算](../../app/modules/operation_event/application/budget.py)与[工具注册表](../../app/modules/operation_event/application/investigation_tools.py)。预算属于应用约束，不能仅写在提示词里。

## 18 MCP、工具、资源、提示模板、HTTP传输与Tasks

MCP约定AI客户端怎样发现和调用服务能力。它解决协议与能力描述，不决定工具结果是否正确，也不替代业务授权。

| 能力 | 含义 | 本项目例子 |
|---|---|---|
| tools | 可调用的能力，带参数Schema | 查询规范、气象预警、提交待确认观察 |
| resources | 可按标识读取的上下文 | 事件上下文、工单验收资料 |
| prompts | 服务提供的任务模板 | 调查交接、独立验收提示 |

Streamable HTTP承载MCP请求与响应，和普通业务REST是两套入口。MCP通常使用JSON-RPC消息，包含方法、参数及请求ID。内部智能体直接调用进程内工具，并不为了遵循MCP形式而绕到自己的HTTP端口。

**基本调用顺序。** 先按协议发现能力，再调用`tools/list`读取参数Schema，然后使用`tools/call`。完整请求还要携带身份及协议元数据，不能只复制下面这个业务参数片段作为完整HTTP请求：

```json
{"name": "get_weather_alerts", "arguments": {"event_id": "实际事件UUID"}}
```

Tasks扩展用于持久长任务：本项目按2026-07-28扩展进行逐请求能力协商，返回任务句柄后由客户端轮询`tasks/get`，通过`tasks/update`提交补证，通过`tasks/cancel`取消。没有协商时不能返回任务句柄。JSON-RPC的请求`id`匹配一次请求与响应；`taskId`标识跨多次查询持续存在的任务，二者用途不同。客户端断开HTTP连接，不等于后台调查被取消。

工具的只读声明是能力说明，业务服务还要真正拒绝越权和不允许的动作。外部助手提交的观察仍是待确认材料，不能自动晋升为现场事实。实现与可运行请求见[MCP服务](../../app/modules/operation_event/api/mcp_server.py)、[Tasks适配](../../app/modules/operation_event/api/mcp_tasks.py)及[协议测试](../../tests/test_mcp_server.py)。

## 19 Agent Skills、SKILL.md、YAML、版本与内容摘要

技能包把专业流程保存成可维护资料。例如泄漏调查应检查哪些事实、必须引用哪些证据、输出哪些未知项。它是受控的程序说明，不是新增事实来源。

`SKILL.md`前面的YAML保存名称、描述和版本，正文保存流程。YAML用键值和缩进组织数据；同一层级的缩进必须一致。简化格式如下，示例名称不属于当前项目技能白名单：

```yaml
---
name: learning-inspection
description: 教学示例，说明技能包结构。
metadata:
  version: "1.0.0"
---
```

**基本使用。** 先读取目录中的名称与摘要，命中任务后再加载正文。更新检查步骤时更新版本，并核对内容哈希。SHA-256把文件内容变成固定长度摘要，便于发现内容变化；同一版本号下文件被改动，也可以被摘要检查发现。

项目只加载仓库内白名单技能，使用PyYAML安全解析元数据；它不执行模型给出的任意路径或脚本。协调者选中技能后，运行保存实际版本及正文，排队期间目录变化不能静默混用。

先读[skills.py](../../app/modules/operation_event/application/skills.py)，再看[技能目录](../../app/modules/operation_event/skills)。阀门技能当前包含按需气象与空间核查，不要求每次调查都调用所有工具。

## 20 短期记忆、长期经验、整合、去重与失效

记忆是为了后续任务能利用先前材料，但保存过不代表一直可信。短期记忆面向当前事件，例如已确认观察与最近候选摘要；长期经验面向跨事件复用，例如某型号设备在特定条件下的处置经验。

```text
原始观察 → 人工确认 → 当前事件事实
调查结果 → 候选摘要 → 只作上下文参考
关闭工单与实测 → 经验草稿 → 独立审核 → 可检索长期经验
```

记忆整合将零散材料整理为结构化经验，保存适用设备、现象、前提、措施、结果及来源。去重可用规范化内容的指纹发现完全相同草稿；相似但不相同的经验仍需比较前提，不能只按相似标题合并。

**基本使用。** 新增观察后先走人工确认，再让新调查读取；经验则核对来源工单及实测后审核。修订创建新版本，替代、合并或撤回保留关系和理由。读取时重新检查权限、有效期、来源版本和设备条件。

Checkpoint保存程序运行状态，和业务记忆用途不同；摘要属于模型候选，也不等于已确认事实。气象这类短时数据过期后，不能因它曾进入记忆而继续当作当前预警。

实现见[memory.py](../../app/modules/operation_event/application/memory.py)、[记忆模型](../../app/modules/operation_event/domain/memory_models.py)与[第12章](../第12章_持续调查与经验记忆.md)。

## 21 上下文工程、角色证据视图与正文卸载

上下文是一次模型请求实际能看到的输入。它有长度和费用限制；把全部历史记录拼进去，会同时引入无关内容、旧版本和来源冲突。

上下文工程决定哪些资料给哪个角色、保留哪些来源信息，以及缺少正文时怎样回查。风险角色需要可用事实，方案角色需要风险与适用规范，复核角色需要重新对照原文。上游角色给出的摘要不能替代来源。

```json
{
  "evidence_id": "证据UUID",
  "source": "knowledge-rag",
  "version": "来源版本",
  "content": {"offloaded": true, "content_hash": "摘要值", "read_tool": "read_investigation_evidence"}
}
```

这类清单保留证据标识和来源，把大正文留在数据库。正文卸载表示改变传输方式，不是删除证据；模型确实需要时用`证据UUID:字符偏移`分块回查。回查必须再次验证访问范围与来源，不能让缓存绕过撤权。

**基本使用。** 先读清单并选择相关证据；存在截断或正文未加载时明确承认范围，不能把“列表里没有”推断成“事实不存在”。项目限制上下文容量，超出能力时应整理材料或补证。

看[context.py](../../app/modules/operation_event/application/context.py)的视图构造与[工具回查](../../app/modules/operation_event/application/investigation_tools.py)，再对照[第5章](../第05章_异常分级与维检工单模块开发.md)。

## 22 GEPA库、轨迹反思、变异、Pareto选择与发布

提示词是模型执行任务时读取的文字指令。提示词优化是在固定任务和评价标准下比较不同指令。[GEPA](https://github.com/gepa-ai/gepa)是实现这种搜索的Python开源库：先执行案例，利用轨迹中的失败原因反思，再提出修改并测量结果。它不会改变Qwen的模型权重；运行优化仍会多次调用模型，消耗时间和API费用。

轨迹包含证据、各角色输出和专家参考。例如模型把条件未知的历史经验当成已证实措施，反思可以提出“先列明适用前提，未知时排除”的规则。候选变异是修改指令，不是修改专家标签迎合输出。

Pareto前沿处理多个比较目标：若候选A在全部目标上不差于B，并至少一项更好，A支配B。互不支配的候选可保留。例如类别/风险准确率分别为90%/80%的A和85%/90%的B互不支配；80%/70%的C被两者支配。风险低估率越低越好，比较时应转换方向。GEPA还会保留在不同案例上表现出优势的候选，避免只根据一个平均分丢弃它们。

**基本使用。** 使用库需要准备三项内容：初始提示词、带评价标准的案例，以及返回评分和错误反馈的评估函数。`gepa.optimize`组织搜索，`GEPAAdapter.evaluate`执行案例并返回`EvaluationBatch`，`make_reflective_dataset`把轨迹整理成反思材料。项目提供`propose_new_texts`，让反思沿现有Qwen接口执行，因此不需要再配置另一套模型密钥。候选选择和接受仍由GEPA引擎负责。

项目依赖固定为`gepa==0.1.4`，随`uv sync --frozen`安装。库的引擎是同步调用，放在工作线程；涉及数据库和模型的操作送回原异步事件循环执行，数据库Session不会跨线程使用。引擎日志不直接输出业务轨迹，结果经原权限控制的优化接口读取。

```text
固定开发案例与证据 → 基线重复测量 → GEPA选择父候选
→ 读取失败轨迹并生成新指令 → 同案例重复测量
→ 保存逐题差异与优势候选 → 生成未启用版本
→ 独立事件完整调查 → 人工标注与验收 → 发布或保留原版本
```

通过`POST /api/v1/prompt-optimizations`提交开发集评测ID，例如参数包含：

```json
{"evaluation_id": "00000000-0000-0000-0000-000000000001", "generations": 2, "repetitions": 2, "max_cases": 4, "max_model_calls": 128, "max_tokens": 500000}
```

示例ID应替换为有权访问的开发集评测ID。`generations`限制提议次数，`repetitions`决定同一案例重复多少次，不保证每次提议都产生新的已接受候选。重复测量能展示波动，不能使模型变成确定程序。本次搜索中重复读取同一候选会复用这些测量；独立验收必须产生新运行。

当前搜索重放风险、方案、复核三个角色，采用类别、风险、引用F1、非低估和引用有效性指标。处置建议的安全性仍由专业人员重新判断。任一案例的低估或引用越界恶化会阻止选择该候选，不能用总分提高掩盖。正式发布还要求其他事件的held_out完整调查、人工标注及已关闭改进验收。

实现见[业务优化任务](../../app/modules/operation_event/application/optimization.py)、[GEPA适配](../../app/modules/operation_event/application/prompt_search.py)，操作与回退见[第11章](../第11章_效果评测与改进验收闭环.md)。
