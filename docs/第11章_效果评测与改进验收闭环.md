# 第11章：效果评测与改进验收

指标把一个明确评价对象与参考标准作比较：检索指标衡量找材料，类别与风险指标衡量判断，建议安全性需要人员标注。开发集用于修改，留出集用于独立验收；GEPA根据开发集轨迹反思和比较提示词候选。

相关基础：[指标定义与计算例子](基础知识/06_效果评测与验收.md#t33)、[数据划分及改进闭环](基础知识/06_效果评测与验收.md#t34)、[提示词优化](基础知识/04_智能体与专业流程.md#t22)。

## 11.1 先区分运行成功与效果合格

任务成功表示程序完成了规定流程；回答有引用表示能够找到来源；专家判断正确与安全，才属于业务效果评价。三者分别验证，不能用HTTP成功率或模型自己给出的质量分代替专家结果。

评测需要数据集、实际输出、参考标注、指标和运行配置。`development`用于发现问题和调参，`held_out`用于检验未参与调整的样本。反复根据held_out结果调参，会削弱它对泛化效果的解释力。

## 11.2 RAG先评价检索

检索评价比较“应找到的证据集合”与“实际返回的有序列表”。例如参考为`{A,B,C}`，返回`[X,B,A]`，其中X无关。

| 指标 | 含义 | 示例 |
|---|---|---|
| Recall | 找到多少应有证据 | 命中A、B，召回率2/3 |
| RR | 第一条相关证据排得多靠前 | B在第2位，RR=1/2 |
| MRR | 多题RR的平均值 | 每题先算RR，再平均 |
| nDCG | 全部相关证据的排序质量 | 越靠前的相关结果权重越大 |

本项目使用二元相关性。第r位相关结果的DCG贡献为`1/log2(r+1)`；不相关结果为0。nDCG用实际DCG除以相同截断范围的理想DCG，理想相关条数最多为`min(参考相关数,实际返回数)`。应该有证据却返回空列表时不能记满分。

实现见[evaluation.py](../app/modules/knowledge/application/evaluation.py)的`retrieval_metrics`。其中`set.intersection`找命中，`enumerate`保留排名，`next`取第一条相关结果；重复证据不会增加召回数。代码中的单题字段`mrr`保存RR，汇总后才是平均值。

## 11.3 稳定原文标注与回答评价

重新分段可能改变片段UUID。为了比较修改前后的检索，样本可使用`document_code + quote`指定参考原文；代码统一空白和大小写，再检查返回文档编号与正文包含关系。这是原文匹配，不是语义相似判断。

`reference_metrics`将参考引文转为评分单元，同一引文只计一次，无关返回仍占排名。一个片段覆盖多条引文时会展开，因此这套引文排名指标不能未经说明就当作原始片段排名。

检索好不代表回答好。RAG评测会保存实际回答、引用、拒答、运行轨迹及耗时，专家按`case_id + mode`标注`answer_correct`、`unsafe_answer`和理由。拒答正确性依据`should_refuse`，不是“所有问题都拒答就安全合格”。

## 11.4 RAG评测怎样执行

`EvaluationCreate`要求名称、数据划分、1–300条问题与检索模式，可提供参考答案、片段ID或稳定原文。评测模式为`hybrid`、`fulltext`、`vector`、`graph`，不包含global。

后台按“问题×模式”重新执行检索、生成和核查。每题重新检查授权，模型与配置来自任务快照。`summarize`做宏平均：每条结果权重相同；耗时统计当前执行过程，不包含排队等待。

若同一道题有两种模式，就形成两个待复核单元。模型核查结果和专家审核分别保存；指标缺失、未复核或来源不可见，不能通过补一个平均数完成验收。

## 11.5 Agent离线评测

Agent评测读取已经成功的调查运行与人工标注，比较类别、风险和引用证据。它本身不重新执行调查，也不修改工单；改进后的复测需要先生成新的调查运行，再建立新的评测。

| 指标 | 方向与解释 |
|---|---|
| 类别/风险判断 | 与人工标签比较 |
| 风险低估率 | 越低越好，防止把高风险评低 |
| 证据Precision | 引用中有多少属于相关证据 |
| 证据Recall | 应引用的相关证据覆盖多少 |
| 证据F1 | Precision与Recall的调和平均 |
| 行动接受率 | 专家是否认为方案可接受 |
| 不安全行动率 | 越低越好，不能用其他高分抵消 |

风险等级使用调查模块的`low/medium/high/critical`顺序，不直接套用隐患模块的`major`。相关证据必须属于该次运行，旧来源撤权后也不能借评测快照读取。实现见[Agent评测](../app/modules/operation_event/application/evaluation.py)。

## 11.6 提示词优化与版本发布

提示词调整是改进措施的一种。[GEPA](https://github.com/gepa-ai/gepa)是Python提示词优化库，读取运行轨迹与评分反馈，提出新指令并搜索候选。它修改角色使用的文本，不训练Qwen权重。项目固定使用`gepa==0.1.4`，由官方引擎管理候选选择、接受和Pareto前沿；业务适配层负责执行调查角色、评分、预算和结果保存。

入口`POST /api/v1/prompt-optimizations`需要提示词管理权限，只接收`development`专家评测。提交`evaluation_id`、`generations`、`repetitions`及案例、模型次数、Token和费用预算。默认最多4个事件、2次候选提议，每个案例重复2次；案例上限8、提议上限4、重复上限3。任务沿现有RabbitMQ、Outbox和Worker运行，通用Job接口负责取消、重试；不会产生新的业务入口或单独优化服务。

先固定事件版本、原调查时刻、证据与技能快照，在同一模型配置下重放风险、方案和复核角色。基线与候选对同一案例重复运行，保存每次输出及分数范围。相同候选和案例在本次搜索中再次被引擎读取时复用已保存的重复结果，避免为获取反思轨迹重复付费；新一次任务仍重新测量。

| 开发评分 | 含义与边界 |
|---|---|
| 类别与风险正确性 | 对照专家类别、风险标签 |
| 引用F1 | 核对三个角色引用的证据与相关证据标注，不等于原文支持性已被专家确认 |
| 非低估指标 | 检查是否低于专家风险等级；任一次重复出现低估即保留该缺陷 |
| 引用有效性 | 引用ID须属于当前案例可用证据；任一次引用越界即保留该缺陷 |

反思输入包含逐角色输出、复核问题、冲突、未知项和专家类别、风险标签。GEPA按每个案例及各目标保留优势候选，项目同时保存候选摘要、反思、逐题重复结果、基线对照差值及引擎父子关系。当前采用单条完整调查指令作为优化组件，不开启候选文本合并，避免在没有多个可独立组合组件时人为拼接指令。若最终候选在任一案例上使风险低估或引用越界恶化，项目保留基线，不允许用其他案例的提高抵消该退步。

这些指标用于搜索，不能证明处置措施安全。旧建议的安全标签不能转给新建议，模型复核通过不能代替专家；开发重放也不衡量协调者是否正确拆分任务和提出人工补证。完整调查能力仍在留出事件上复测。模型调用前限制输入输出与剩余预算；供应商缺少用量时单独保留保守估计，不按零费用放行。取消在调用检查点生效，已发送的模型请求不能保证立即终止。

候选写入普通`event.classify`提示词版本，默认不启用。管理员可在正式分类请求中显式传`prompt_candidate_id`进行受控复测。发布流程：

1. 使用未参与开发的其他事件建立`held_out`基线，登记改进问题、措施和验收目标。
2. 记录实施后，以候选版本重新执行完整调查，由人员重新标注建议安全性及效果，创建新held_out评测。
3. 沿原改进接口复测、独立验收，保留前后指标；风险低估率和不安全建议率必须为0。
4. 调用`POST /api/v1/prompt-optimizations/{id}:publish`，提交已关闭的`improvement_id`和理由。后端检查事件隔离、候选版本和验收结果，再激活版本并审计。

发布后若需回退，通过现有`POST /api/v1/admin/prompt-templates/{template_id}:activate`重新激活原来已批准的版本，填写原因；未验收的优化候选不能通过此入口绕过发布。运行配置冻结提示词版本，回退影响后续调查，不改写历史运行。

实现见[optimization.py](../app/modules/operation_event/application/optimization.py)与[官方引擎适配](../app/modules/operation_event/application/prompt_search.py)，测试见[搜索与发布](../tests/test_investigation_extensions.py)和[多步取证与GEPA](../tests/test_investigation_followups.py)。真实百炼效果需要实际标注数据验证；测试中的合成结果只证明调用、比较和约束成立。

## 11.7 从评价走到改进验收

```text
基线评测 → 人工确认问题、措施和目标 → 分派执行人与独立验收人
→ 记录实际实施与版本 → 修改后生成新运行/新评测
→ 同集比较前后指标 → 独立验收 → closed或退回
```

改进记录状态为`confirmed → implemented → retested → closed`。创建时保存问题、措施、基线、目标、负责人、验收人和期限；实施时记录具体变化与代码、提示词或配置版本。

复测必须是实施之后创建的新评测。Agent运行也须在实施之后启动，不能拿旧运行换个评测ID；数据划分和样本身份需要可比。多模式RAG目标使用带模式前缀的指标，避免平均值掩盖某一模式退步。

验收目标要求Agent风险低估率、不安全建议率及RAG不安全回答率为0。实际指标缺失或不达标，独立验收不能关闭。历史保存基线、复测、目标判断、实施版本和人员决定。

## 11.8 代码与验证

[quality应用服务](../app/modules/quality/application/service.py)负责快照、可比性、目标和状态；[Schema](../app/modules/quality/domain/schemas.py)约束输入；[改进测试](../tests/test_evaluation_improvements.py)验证完整闭环，[回答复核测试](../tests/test_evaluation_answer_review.py)覆盖专家标注。

准备样本时保留真实来源、业务专家标签和标注理由。合成测试用于验证规则，不能替代企业效果样本，也不能由模型自行补写正确答案来证明自己达标。
