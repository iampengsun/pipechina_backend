## 04 SQLAlchemy ORM、异步Session、事务与并发控制

**先认识ORM（对象关系映射）。** 关系数据库保存表、行和列；ORM将它们映射为类、对象和属性。SQLAlchemy既能表达SQL查询，也能跟踪对象变化。它不替代数据库约束，更不会自动知道“工单已经验收”之类业务规则。

Engine管理连接及连接池。Session跟踪一次业务操作读取和修改的对象，并管理事务。异步Session在等待数据库IO时让出执行权，但同一个Session不能随意交给多个并发分支共享。

下面是项目已有模型上的查询形状，调用者提供会话和当前用户；返回ORM对象后仍应按接口Schema转换响应：

```python
from sqlalchemy import select
from app.modules.operation_event.domain.models import ProductionEvent


async def read_own_events(session, user_id):
    statement = select(ProductionEvent).where(ProductionEvent.created_by == user_id)
    return list(await session.scalars(statement))
```

`select`构造查询，`where`增加条件，`scalars`取每行中的模型对象。这个教学函数只有本人条件，正式接口还需使用项目的数据范围规则。

**事务的基本顺序。** `session.add`登记待保存对象；`flush`将变更发送到当前事务，便于取得主键或发现约束冲突；`commit`提交整笔事务；`rollback`撤销未提交变更。`flush`不等于其他连接已经看见这些结果。

行锁让并发事务对同一关键记录排队，常见SQL为`SELECT ... FOR UPDATE`。锁应保护关键检查与修改，事务结束后释放。乐观版本检查则要求客户端提交`expected_version`；服务器发现版本不一致时拒绝覆盖。二者可以同时使用：锁处理并发交错，版本处理过期请求。

**在本项目中。** [db.py](../../app/shared/db.py)创建会话工厂，[站场位置服务](../../app/modules/operational_graph/application/locations.py)展示锁、版本、追加记录与审计。并行调查分支各自创建Session，再通过数据库锁共享预算，见[subinvestigations.py](../../app/modules/operation_event/application/subinvestigations.py)。

## 05 PostgreSQL、JSONB、索引、外键、约束与触发器

PostgreSQL是保存正式业务数据的关系数据库。表有明确列类型；主键唯一标识记录；外键要求关联目标存在；唯一约束防止重复业务编号；检查约束限制数值或状态。数据库约束可以同时约束来自不同进程的写入。PostgreSQL里的Schema是表等对象的命名空间，例如`public`；它和Pydantic/JSON Schema所说的“数据结构描述”不是同一个概念。

**最小练习。** 在独立数据库连接中执行：

```sql
BEGIN;
CREATE TEMP TABLE learning_event (
    id integer PRIMARY KEY,
    code text UNIQUE NOT NULL,
    pressure numeric CHECK (pressure >= 0),
    detail jsonb NOT NULL
);
INSERT INTO learning_event VALUES
    (1, 'LEARNING-1', 6.0, '{"source":"software-example"}');
SELECT code, detail ->> 'source' AS source FROM learning_event;
ROLLBACK;
```

临时表只属于当前会话；事务回滚后练习变更撤销。`->>`从JSONB取出字段的文本值。JSONB适合结构化快照与可变化属性，但重要业务关联仍应使用明确列及外键，不能把所有规则都藏进JSON。

索引是帮助数据库定位数据的附加结构，例如按事件与状态组合查找活动任务。索引占空间并增加写入成本，应围绕实际查询建立；索引存在也不保证所有查询都会使用它。查询计划可用`EXPLAIN`查看；`EXPLAIN ANALYZE`会真的执行语句，学习时选择只读查询。

触发器在指定表操作发生时自动执行数据库函数。本项目用它记录业务图谱变更，再由后台投影；触发器没有在同一事务里直接调用Neo4j。

**在本项目中。** 业务模型使用[JSON_DOCUMENT](../../app/shared/types.py)映射JSON类型，表结构由[迁移目录](../../alembic/versions)维护。图谱变更来源与注册见[change_capture.py](../../app/modules/operational_graph/application/change_capture.py)。PostgreSQL保存正式状态，搜索索引和图谱是可重建的查询投影。

## 06 asyncpg与psycopg：数据库驱动

驱动负责连接PostgreSQL、发送SQL、编码参数和读取结果。SQLAlchemy是更上层的查询与对象管理工具，驱动完成实际通信。连接字符串中的`postgresql+asyncpg`表示SQLAlchemy使用asyncpg异步驱动。

psycopg也提供PostgreSQL访问能力；项目的LangGraph PostgreSQL检查点组件使用相关连接能力，测试准备与部分工具还使用同步连接。它与asyncpg不是两个数据库。

下面是psycopg同步只读查询的形状，`database_url`由调用者提供，不在示例中写账号或口令：

```python
import psycopg


# database_url采用postgresql://形式，由配置或安全环境提供。
def database_version(database_url):
    with psycopg.connect(database_url) as connection:
        with connection.cursor() as cursor:
            cursor.execute("SELECT version()")
            return cursor.fetchone()[0]
```

业务代码通常通过SQLAlchemy会话访问，不需要同时手写两套连接。同步数据库调用会占用当前线程；不能因为外层函数写了`async def`，就认为其中的同步调用自动变成非阻塞。

## 07 Alembic、迁移版本、升级与回退

修改ORM类不会自动修改已存在的数据库。Alembic用有顺序的迁移脚本记录结构变化，例如增加站场位置表；版本表记录数据库已经执行到哪一步。迁移脚本和业务记录版本是两件事。

**基本用法。** 从项目根目录检查：

```bash
uv run alembic current
uv run alembic heads
uv run alembic check
```

`current`读当前数据库版本，`heads`读迁移代码的最新分支头，`check`比较数据库与模型是否存在待记录差异。连接目标来自项目配置，先确认它是预期环境。部署时的`upgrade head`会真正修改结构，应沿项目启动或部署流程执行。

一份迁移包含`revision`、`down_revision`、`upgrade`和`downgrade`。上行脚本描述变化，下行脚本描述回退；回退可能删除数据，不能把它当普通撤销按钮。自动生成只提供差异草稿，数据转换、约束命名和触发器仍要核对。

**在本项目中。** `0001`是首版基线，`0002_agent_tasks`加入等待输入与提示词搜索，`0003_station_locations`加入位置版本。见[alembic/versions](../../alembic/versions)与[结构核查脚本](../../scripts/verify_postgres_schema.py)。[迁移测试](../../tests/test_initial_schema.py)在可丢弃测试库验证建库、差异、回退和重建。
