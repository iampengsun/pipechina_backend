# 后台任务、访问控制与文件存储基础

本篇对应08—14。把一次长任务拆成“业务记录、消息交付、执行进程、外部文件”来看，更容易理解失败后该从哪里恢复。

<a id="t08"></a>
## 08 Celery、Worker、Beat与任务路由

Celery是后台任务框架。API登记任务并安排投递，Worker进程接收任务后运行Python函数；Beat按计划发起周期任务。Beat负责“什么时候投递”，Worker负责“实际执行”。

```text
API / Beat → 任务消息 → RabbitMQ队列 → Worker → 应用服务 → 数据库结果
```

任务名称标识执行函数，参数应是可传输的数据，例如Job UUID；不能把数据库Session或打开的文件句柄塞进消息。队列路由将不同工作分开，例如音频、调查、知识解析和维护任务。

**基本使用与观察。** 先通过项目启动工具启动，再检查：

```bash
python3 scripts/manage_stack.py status
python3 scripts/manage_stack.py logs
```

本项目的受理响应包含Job ID。应结合Job状态和Worker日志确认结果，不能把Celery消息已发送或HTTP 202当作业务成功。

[celery_app.py](../../app/bootstrap/celery_app.py)登记任务模块、队列与Beat计划；[事件任务](../../app/modules/operation_event/application/tasks.py)展示如何加载Job和固定来源版本。多个Worker可以处理不同任务，正式写回仍须通过租约及业务条件检查。

<a id="t09"></a>
## 09 RabbitMQ、AMQP、交换机、队列与确认

RabbitMQ是消息代理：暂存并交付消息，不执行Python业务代码。AMQP是生产者、代理和消费者之间使用的消息协议。生产者发布消息，交换机根据路由规则将消息送入队列，消费者再接收。

| 名称 | 基础含义 |
|---|---|
| Exchange / routing key | 交换机和路由键，用于选择队列 |
| Queue | 等待消费的消息集合 |
| Ready | 仍在队列中等待交付 |
| Unacked | 已交付给消费者，尚未确认 |
| Publisher Confirm | 代理向发布者确认接收消息 |
| ACK | 消费者向代理确认本次交付 |

Publisher Confirm不能证明业务完成；ACK也不能替代数据库事务。进程在写库后、ACK前崩溃时，消息可能重投，因此需要业务幂等。

**只读观察。** 项目启动后可查看队列数量：

```bash
docker compose --env-file .env -f infra/compose/project.yml exec rabbitmq \
  rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
```

长任务存在时Unacked不一定是故障；Ready持续增长且没有消费者则要检查Worker及路由。队列瞬间为空，也可能只是消息已快速消费。[第2章](../第02章_公共基座搭建启动与测试.md)继续讲消息持久化、重投与Outbox，配置见[Compose](../../infra/compose/project.yml)。

## 10 Redis、缓存、TTL、限流与任务结果后端

Redis把数据组织成键值及其他内存数据结构，适合快速共享短期状态。TTL是键的剩余生存时间，过期后删除；它不能代替正式业务记录的保留策略。

下面是Redis命令语义示例，键名前缀表示学习数据，示例不由本次文档修改自动执行：

```text
SET learning:status queued EX 60
GET learning:status
TTL learning:status
```

第一条保存值并设置60秒过期，后两条查看值和剩余时间。缓存表示可重新得到的副本；Celery结果后端保存任务框架结果；限流记录某个时间窗中的请求数。三者都不等于PostgreSQL里的正式Job状态。

本项目使用Redis支持Celery结果和请求限流。限流脚本把计数与首次设置过期时间放在同一次原子操作中，避免多个API进程各自记账。Redis不可用时的行为由[operations.py](../../app/shared/platform/operations.py)明确处理，不能把连接失败当作计数为零。

**本项目练习。** 发起有限次数的普通API请求，观察响应与限流配置；不向正式限流键写测试值。连接和端口见[配置](../../app/bootstrap/config.py)与[Compose](../../infra/compose/project.yml)。

## 11 事务Outbox、幂等、重试、租约、心跳与取消

数据库提交与发送消息属于两个系统，无法靠一次普通数据库事务同时完成。若写库后进程还没发送消息就崩溃，任务可能永远没人处理。Outbox将“待发送的消息”作为数据库记录，与业务变化一起提交，再由后台发布。

```text
同一事务：创建Job + 创建Outbox → 提交
后台：读取Outbox → 发送消息 → 保存投递状态
Worker：领取租约 → 执行 → 检查令牌与业务条件 → 提交结果
```

发送成功后、保存投递状态前也可能崩溃，消息仍会重复。因此幂等表示“同一业务请求重复到达时，结果不会多执行一份”。请求编号必须和相同参数绑定；复用编号发送不同内容应冲突。

重试是重新尝试失败操作，不代表可以跳过来源版本、权限或审批。租约表示某个Worker在一段时间内拥有执行权；心跳延长租约；执行令牌区分不同尝试。租约过期后即使旧Worker醒来，也不能凭旧令牌覆盖新结果。

协作取消表示先登记取消意图，由执行过程在受控检查点停止。等待输入或排队中的任务可以直接结束；正在进行的外部HTTP请求不一定能立刻停止。`waiting_input`是可恢复状态，不是执行失败，也不应让Worker无限占着线程等待。

**基本用法。** 客户端保存返回的Job ID，读取`GET /api/v1/jobs/{job_id}`；取消和重试使用各自接口。重试后核对新Job及对应业务运行，而不是手动改数据库状态。实现见[平台服务](../../app/shared/platform/service.py)、[执行租约](../../app/shared/platform/execution.py)和[调查恢复](../../app/modules/operation_event/application/input_requests.py)。

## 12 JWT、JWKS、RS256、签名验证与身份提供方

身份提供方签发令牌，后端验证令牌后确定当前用户。JWT常见外形是由点分隔的三段：头部、声明、签名。编码不是加密，不能因为内容看不懂就把它当作保密容器。

RS256使用私钥签名、公钥验证。JWKS是发布一组公钥及其标识的格式，支持按`kid`选钥和密钥轮换。PyJWT处理JWT解析与校验，cryptography提供底层密码能力。

```text
用户从身份服务取得令牌 → Authorization: Bearer <token>
→ 验证签名、有效期、issuer、audience → 加载本地账号与授权
```

`issuer`表示谁签发，`audience`表示令牌发给谁。只解码正文、不验证签名和这些条件，不能作为认证。令牌有效也不代表账号仍有效，项目还检查本地账号、组织和授权。

**基本使用。** 在本地开发环境向Mock IdP取得测试令牌，再在API请求头携带Bearer。不要把完整令牌写入文档、Git或日志；本机Mock IdP不代表已经完成企业单点登录部署。

实现入口：[认证依赖](../../app/shared/security/authentication/dependencies.py)、[身份仓库](../../app/shared/security/identity/repository.py)和[Mock IdP](../../dev/mock_idp/main.py)。本项目消费身份令牌并管理本地授权，不能把这些代码当作完整OAuth交互登录流程。

## 13 RBAC、权限点与数据范围

RBAC按角色组织权限。权限点回答“能执行什么动作”，数据范围回答“能对哪些记录执行”。例如拥有`event:read`但范围只有本人时，不应读到其他人创建的事件。

| 检查 | 示例 |
|---|---|
| 身份 | 当前请求是谁 |
| 操作权限 | 是否允许读取事件 |
| 数据范围 | 本人、本组织、组织子树、执行人或全局 |
| 来源约束 | 引用知识、会议或经验是否仍可见 |
| 状态/版本 | 记录是否确认，版本是否仍对应本次操作 |

ACL是访问控制列表，用来记录某份资料允许哪些账号读取。它与按角色分配操作权限互补，因此有知识读取权限仍可能无权读取特定会议来源。

**基本用法。** 在查询时加入数据范围条件，而不是先取全表再交给模型筛选；读取单条记录及重要写入仍需检查。接口的UUID参数校验只能证明格式，不能证明访问资格。

项目通过`require_permission`检查权限点，通过`data_scope_clause`生成查询过滤，通过`require_data_scope`检查具体对象。看[授权依赖](../../app/shared/security/authorization/dependencies.py)和[权限目录](../../app/shared/security/authorization/permissions.py)，再对照[站场位置服务](../../app/modules/operational_graph/application/locations.py)。异步任务会重新加载发起人的当前权限，防止排队期间撤权后继续发布。

## 14 S3、SeaweedFS、boto3、签名URL与multipart

对象存储用Bucket和对象键定位完整文件，适合音频、图片、文档与导出物。数据库保存业务归属、版本和对象引用，文件字节由存储服务保存。S3是一套常用对象存储API；本项目SeaweedFS提供兼容接口，boto3是调用这一类接口的SDK。

签名URL将某个方法、对象和有效期绑定为临时授权，取得它的人在期限内可能拥有指定操作能力。它不是永久公开链接。`multipart/form-data`是HTTP表单/文件编码；S3分片上传是把大对象拆成多部分上传，二者名字相近但属于不同机制。

**最小业务流程。**

```text
创建业务记录并声明文件信息 → 服务端签发上传授权
→ 客户端按授权上传实际字节 → 通知上传完成
→ 服务端检查对象、长度、摘要及类型 → 才允许进入模型处理
```

客户端传来的文件名、MIME和大小只是声明。上传完成回调也不是“文件可信”的证据，服务端仍须读取或检查存储对象。下载同样先检查当前业务权限，再提供受限访问方式。

实现通过[存储端口](../../app/ports/storage.py)提供统一能力，装配见[providers.py](../../app/bootstrap/providers.py)，验证入口见[媒体共享代码](../../app/shared/media)。[第3章](../第03章_调度交接班记录模块开发.md)演示录音上传业务；本地文件和内存适配器主要服务开发与测试。
